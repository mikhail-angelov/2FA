# Спецификация: 2FA-аутентификатор (Android)

Статус: **реализовано** · 2026-10-01 · репозиторий <https://github.com/mikhail-angelov/2FA>

Лаконичный TOTP-аутентификатор: один экран, минимум зависимостей, шифрование секретов на
устройстве, зашифрованный экспорт/импорт через SAF.

Это исправленная и дополненная версия исходного текста спецификации. Раздел «Что поправлено»
перечисляет расхождения с исходником и их причины — в том числе ошибки, попавшие в
присланный код.

---

## 1. Стек

| Слой | Выбор | Примечание |
|---|---|---|
| Язык и UI | Kotlin, Jetpack Compose, один экран | single-activity, `MainActivity` |
| Хранилище | Room + шифрование столбца секрета ключом Android Keystore | см. §3.2 — почему не SQLCipher и не EncryptedSharedPreferences |
| Сканер QR | `com.google.mlkit:barcode-scanning:17.3.0` + `androidx.camera:camera-{camera2,lifecycle,view}:1.5.0` | формат QR, первый распознанный `otpauth://totp/…` |
| Иконки сервисов | Coil `2.6.0` + встроенная таблица «сервис → домен + цвет» | монограмма рисуется локально, фавикон подтягивается по сети |
| TOTP | `javax.crypto` (HMAC-SHA1/256/512) | внешних крипто-библиотек нет |
| Экспорт | PBKDF2-HMAC-SHA256 (210 000) + AES-256-GCM | тоже только JDK: `javax.crypto` |
| Инструменты | AGP 9.1.0, Kotlin 2.3.10, Gradle 9.6.1, compileSdk 37, minSdk 26 | набор, проверенный на сборочной машине |

Зависимости приложения по существу три: база (Room), сканер (ML Kit + CameraX) и картинки
(Coil). Всё остальное — AndroidX и JDK.

## 2. Экран

`HomeScreen` (файл `ui/HomeScreen.kt`):

1. **TopBar** — название, поле поиска, кнопка «Экспорт/импорт».
2. **Поиск** фильтрует по сервису и по аккаунту, без учёта регистра.
3. **Адаптивная сетка** — 1 колонка в портрете, 2 в альбомной ориентации:
   `val columns = if (isLandscape()) 2 else 1` → `LazyVerticalGrid(GridCells.Fixed(columns))`.
4. **Карточка аккаунта** (`ui/OtpCard.kt`) — иконка сервиса, название, аккаунт, код крупным
   моноширинным шрифтом с разрядкой (`382 910`), круговой таймер. Тап по карточке копирует
   код и показывает снекбар; в последние 5 секунд кольцо становится янтарным.
   Удаление требует подтверждения в снекбаре — случайный тап аккаунт не удаляет.
5. **FAB** — нижний лист с выбором «Сканировать QR» / «Ввести вручную».
6. **Часы одни на весь список**: один `LaunchedEffect` раз в секунду обновляет время, коды и
   кольца пересчитываются от него. Так все карточки тикают синхронно, а не каждая сама по себе.

Отдельного экрана-«диалогов» нет: сканер — полноэкранный оверлей, остальное — Compose-диалоги.

## 3. Функциональные требования

### 3.1. QR и ручной ввод

`otp/OtpAuthUri.kt` разбирает `otpauth://totp/Издатель:аккаунт?secret=…&issuer=…&digits=…&period=…&algorithm=…`:

- `secret` — Base32, регистр и пробелы нормализуются;
- `issuer` — параметр URI приоритетнее префикса метки; при отсутствии берётся префикс, при
  отсутствии и его — сам аккаунт;
- `digits` (6..8, по умолчанию 6), `period` (по умолчанию 30), `algorithm` (SHA1/256/512).
- **HOTP и всё, что не `totp` — отклоняется** явно, а не угадывается: возвращается `null`, а
  пользователь видит «Это не TOTP-код».
- Обратная функция `build()` собирает URI — используется при экспорте.

Ручной ввод — те же три поля (сервис, аккаунт, ключ), ключ проверяется попыткой вычисления
кода, при ошибке показывается, что он не похож на Base32.

### 3.2. Хранилище и шифрование

`data/SecretCipher.kt` шифрует Base32-секрет алгоритмом AES-256-GCM на ключе, который живёт
в Android Keystore (там, где устройство умеет — с аппаратной защитой) и не покидает его.
В базе лежит только `iv || ciphertext+tag` в base64; открытого секрета на диске нет.

Почему не так, как в исходном тексте:

- `androidx.security:security-crypto` (EncryptedSharedPreferences) **объявлен deprecated
  upstream** — тянуть его ради того, что Keystore умеет сам, нерационально;
- SQLCipher шифрует файл целиком, но это крупная нативная библиотека (`.so` под каждую ABI),
  что прямо противоречит цели «минимум зависимостей».

Что чувствительного в этой базе — сам секрет; его и шифруем. Число зависимостей от этого
решения — ноль.

Дополнительно: `android:allowBackup="false"` — база аутентификатора не должна уезжать в
андроидный облачный бэкап. Экспорт (зашифрованный, с паролем) — единственный способ вынести
данные.

### 3.3. Иконки сервисов

`icons/IssuerIcons.kt`, три ступени:

1. встроенная таблица популярных сервисов (домен + фирменный цвет), поиск по точному имени,
   затем по отдельным словам названия («Amazon Web Services» → `amazon`);
2. Coil подтягивает фавикон по домену (`https://icon.horse/icon/<домен>`);
3. если сети нет или сервис неизвестен — рисуется круг фирменного (или устойчиво-хешевого)
   цвета с первой буквой названия.

Комплект из ~40 векторных брендов в `res/drawable` **не поставляется намеренно**: рисовать
их руками долго, а поставка чужих логотипов — отдельный лицензионный вопрос. Иконка при этом
есть всегда, в том числе офлайн.

Приватность: фавикон уходит на сторонний сервис, то есть имя сервиса (не секрет!) покидает
устройство. Это цена п. 2; при желании п. 1–3 можно отключить одной строкой.

### 3.4. Экспорт и импорт

`vault/VaultFormat.kt`, `vault/VaultCrypto.kt`, `vault/VaultCodec.kt`, `ui/VaultDialogs.kt`.

Конверт файла читаем намеренно — по нему видно, что это и чем зашифровано:

```json
{
  "format": "2fa-vault",
  "version": 1,
  "kdf": "PBKDF2-HMAC-SHA256",
  "iterations": 210000,
  "cipher": "AES-256-GCM",
  "data": "<base64: salt || iv || ciphertext+tag>"
}
```

Внутри `data` — JSON со списком аккаунтов (сервис, аккаунт, Base32-секрет, алгоритм,
цифры, период). Пароль → PBKDF2 (210 000 итераций) → ключ → AES-256-GCM: одна примитива
и аутентифицирует, и шифрует, поэтому неверный пароль и подделанный файл падают одинаково
громко (`AEADBadTagException`), а не дают мусор.

Экспорт: пароль + подтверждение → системный «создать документ» (SAF) → файл в любой папке,
куда пользователь разрешит запись. Импорт: выбрать файл → пароль → расшифровка и слияние;
дубликаты отсекаются по секрету (см. §3.5), показывается, сколько добавлено и сколько уже было.

**Aegis-совместимость: не поддерживается.** Формат Aegis использует scrypt, которого в JDK
нет — его пришлось бы тянуть через BouncyCastle, что противоречит цели минимальных
зависимостей. Импорт Aegis-файлов — отдельная задача (см. §6).

### 3.5. Импорт из Google Authenticator (скриншот)

`migration/GoogleAuthMigration.kt`, `migration/MigrationImport.kt`,
`migration/ProtobufReader.kt`; вызов — пункт «Импорт из скриншота» в нижнем листе.

Поток: системный **PhotoPicker** (`PickVisualMedia`) → приложению достаётся один `Uri` →
ML Kit распознаёт QR на картинке → проверяется схема `otpauth-migration://` → base64 →
разбор protobuf → секреты кодируются в Base32 (тем же кодировщиком, что и везде) → запись в базу.

**Разрешений не требуется вовсе**: PhotoPicker возвращает доступ к одному выбранному
изображению, поэтому ни `READ_MEDIA_IMAGES`, ни `READ_EXTERNAL_STORAGE` в манифесте нет.

**Protobuf разбирается вручную** — без `protobuf-javalite` и без Gradle-плагина `protoc`.
Формат сообщения заморожен (это формат переноса выпущенного приложения), полей семь;
собственный читатель (varint + length-delimited, около 80 строк) ревьюится глазами и не тянет
ни рантайм-зависимость, ни скачиваемые бинарники. Схема при этом остаётся в репозитории —
`app/src/main/proto/google_auth_migration.proto` — как единственное место, где формат
зафиксирован в стандартной нотации. Неизвестные поля пропускаются, поэтому более новый
сборщик Google импорт не сломает.

**Что пропускается осознанно, с подсчётом в сообщении:**
- **HOTP** (счётчиковые) — приложение только TOTP-ное, и импортировать счётчиковый секрет хуже,
  чем честно сказать «пропущено счётчиковых: 3»;
- **MD5** — таких выпусков в природе нет, и подставлять вместо него что-то похожее нечестно.

**Набор из нескольких QR.** Если аккаунтов много, Google показывает набор кодов («1 из 3»).
Части собираются в памяти и **в базу пишутся только когда пришла последняя**: половина набора
создала бы дубликаты, которых пользователь не видит. Между скриншотами выводится
«Импортирована часть 1 из 3. Загрузите следующий скриншот».

**Дубликаты** отсекаются по самому секрету, а не по подписи карточки: один и тот же аккаунт из
скриншота приходит с чуть другим именем, а секрет совпадает байт в байт. Сравнивать шифротекст
в SQL нельзя — у каждой строки свой IV, — поэтому сравнение идёт по расшифрованным значениям,
которые и так расшифрованы для показа.

**Как читается картинка (1.0.2).** Файл читается в байтах самим приложением
(`contentResolver.openInputStream` → `readBytes` → `BitmapFactory.decodeByteArray`), потому что
`InputImage.fromFilePath` резолвит `content://` через колонку `DATA` MediaStore, которой
системный PhotoPicker не заполняет. Байты декодируются в `ARGB_8888`: ML Kit отвергает bitmap
в другом формате, а декодер JPEG отдаёт RGB_565. Детектору предлагаются три варианта одной
картинки, по порядку — как есть; каждый целевой размер в трёх видах (просто увеличенный,
с белым полем, с полем и бинаризацией по Оцу); сканирование прекращается на первом успехе,
поэтому в памяти живёт не больше одного увеличенного bitmap за раз. Целевых размеров два —
**952 px и 1600 px** по длинной стороне. Это не перестраховка: проверенный образец 238×236
читается ровно при ×4 (952 px) и **не** читается ни при ×2 (476 px), ни при 1600 px —
локальная проверка `cv2.QRCodeDetector.detectAndDecodeMulti` дала на ×4 853 знака
(`otpauth-migration://…`). Коэффициенты считает `ui/ImagePrep.kt` — чистая арифметика над
пикселями, покрыта юнит-тестами.

**Диагностика.** Раньше любая неудача чтения давала одну фразу «Не удалось открыть
изображение», по которой нельзя было понять причину. Теперь сообщение её называет
(«провайдер не отдал данные», «файл не распознан как картинка (N Б)», «QR-код переноса не
найден: картинка WxH, проверено вариантов N»), а в logcat с тегом `OtpImport` попадают
размеры картинки, число вариантов, результат каждого из них и текст исключения детектора.

### 3.6. Безопасность

- `FLAG_SECURE` в `MainActivity` — ни скриншотов, ни превью в списке недавних задач.
- Буфер обмена очищается через 30 секунд после копирования кода, и только если там всё ещё
  лежит именно скопированный код.
- Пароль экспорта не сохраняется нигде и не попадает в логи.
- Секреты расшифровываются только в памяти экрана; списки и сетки работают с ними уже
  расшифрованными и не пишут их на диск.
- Нечитаемая строка (сброс ключа, порча блоба) не роняет список — такая карточка просто не
  показывается, остальные работают.

## 4. Алгоритм TOTP

`crypto/Totp.kt` — RFC 4226 §5.3 (динамическое усечение) и RFC 6238 (счётчик из времени).
Только `javax.crypto`, никаких библиотек.

Две поправки к присланному коду:

1. **Сбитые константы.** В исходном тексте в трёх местах вместо числа оказался emoji:
   `shl 😍`, `ByteArray(cleanInput.length * 5 / 😍`, `if (bitsLeft >= 😍`. Правильные значения:
   `shl 8`, `/ 8`, `>= 8`.
2. **Арифметика.** В исходнике код брался как `binary % 10.0.pow(digits).toInt()` — через
   `Double`. Усечение по RFC даёт 31-битное целое, и гонять его через плавающую точку
   незачем: в рабочей версии целочисленный `% 10^digits`, без промежуточных `Double`.

Base32 (`crypto/Base32.kt`) терпим ко входу так, как секреты реально живут: регистр, пробелы,
дефисы и `=` игнорируются, посторонний символ — явная ошибка, а не тихо выброшенный.

Тесты (`app/src/test/java/.../crypto/TotpTest.kt`) проверяют **векторы RFC 6238 Приложения B**
для SHA1, SHA256 и SHA512 — шесть моментов времени каждый, восемь цифр. Ключи в тесте
собираются из ASCII-байтов, заданных в RFC, и прогоняются через наш же кодировщик Base32:
один тест проверяет и математику TOTP, и кодек Base32.

## 5. Сборка и релиз

### 5.1. Локально

```bash
# SDK и кеш — в /data, JDK 17 запускает Gradle (сам toolchain — JDK 21, Gralde скачает его сам)
export ANDROID_HOME=/data/sdks/android/sdk ANDROID_SDK_ROOT=$ANDROID_HOME
export GRADLE_USER_HOME=/data/gradle
printf 'sdk.dir=%s\n' "$ANDROID_HOME" > local.properties

systemd-run --user --scope -q -p MemoryMax=6G -p MemorySwapMax=1G \
  ./gradlew :app:testDebugUnitTest :app:assembleDebug --console=plain
```

4 ГБ на эту сборку не хватает (ядро убивает демон Gradle) — нужен потолок 6 ГБ. Ограничивать
надо RSS через systemd (`MemoryMax=`), а не адресное пространство: `ulimit -v` ломает JVM.

### 5.2. CI

- `.github/workflows/ci.yml` — на каждый push и PR: юнит-тесты + debug-APK в артефакты.
- `.github/workflows/release.yml` — на тег `v*`: тесты, подписанный release-APK, проверка
  подписи, прикрепление APK к релизу.

**Поправка к исходному тексту.** В присланном варианте подпись выполнялась сторонним экшеном
`r3d-act/signed-apk-android@v2`, которому передаются keystore и оба пароля. Здесь подпись
делает сам Gradle: keystore материализуется из секретов внутри job, `keystore.properties`
пишется локально, после сборки файлы стираются (`shred`). Так пароли подписи не видит ни
один сторонний экшен — что для сборки аутентификатора важно.

Секреты репозитория: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`.
Без них релиз собирается неподписанным, о чём workflow честно предупреждает.

## 6. Что осталось за рамками

- **HOTP** (счётчик вместо времени) — не поддерживается намеренно, чтобы случайный ввод не
  создавал аккаунт, который никогда не даст правильный код. В импорте из Google Authenticator
  такие записи пропускаются с подсчётом (см. §3.5).
- **Импорт Aegis/andOTP** — требует scrypt и, вероятно, отдельной зависимости.
- **Группы, шаблоны, заметки к аккаунтам** — следующая итерация.
- **Автозаполнение и Android Autofill framework** — отдельная тема, здесь не трогалась.
- **Биометрическая защита приложения** — логичное продолжение, но требует решения о том,
  что защищать: вход в приложение или расшифровку конкретного секрета.
